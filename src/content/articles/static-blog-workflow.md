工程记录的价值，往往在问题已经解决之后才显现。过了几周再遇到相似现象，能否找到当时的依据、判断和验证，会直接影响下一次排查的效率。

## 让内容独立于界面

这个博客把正文保存在 Markdown 文件中，标题、简介、分类和日期写在文章开头。界面由 Astro 生成，内容和布局可以分别维护。

新增文章时，先写清楚要回答的问题，再补充背景、做法和结论范围。文章可以是方法总结，也可以是一次可以公开的实践记录。内部环境、客户数据和私人配置不需要出现在公开笔记里。

## 从写作到预览

我希望维护博客像修改一个普通项目一样直接。启动本地预览后，文章与页面修改可以实时查看；正式发布前，再做一次类型与构建检查。

```bash
npm ci
npm run dev
```

写作时也可以使用表格、代码块和数学公式。比如整理检查覆盖情况时，用一个明确的比例表达范围：

$$
C = \frac{N_{\mathrm{checked}}}{N_{\mathrm{planned}}}
$$

这个比例只反映指定检查项的完成情况，不能独立代表整个系统的可靠性。

## 把发布变成固定步骤

文章、项目页、搜索索引、RSS 和 sitemap 在构建时一起生成。发布的是静态文件，访问页面时不需要运行一个网站后端。

```bash
npm run check
npm run build
npm run verify
```

检查完成后，通过 GitHub Pages 发布生成的文件。评论和点赞由独立服务保存；没有配置评论服务时，正文和其他页面仍然可以使用。

## 让记录保持可修订

工程笔记不必在第一次发布时就覆盖所有问题。先说明当前结论的依据，后续发现新证据时再修改。相比追求一篇包罗万象的文章，我更希望每篇记录都能准确回答一个具体问题。
