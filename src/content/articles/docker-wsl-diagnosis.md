在 Windows 上遇到 Docker 命令失败时，我会先留下原始错误和触发命令，再确认故障发生在哪一层。终端能找到 WSL 命令，只说明系统能定位这个程序；还需要单独确认目标发行版能否执行简单命令。发行版能够运行以后，再检查 Docker 引擎、集成设置与具体容器。

## 区分终端与运行环境

这几层值得分开看。Docker Desktop 使用 WSL 2 后端时，可以从 Windows 终端运行 Docker 命令；某个 Linux 发行版中的命令访问，则还涉及该发行版的 WSL 集成。因此，一个终端里的成功或失败，不能直接代表另一个环境的状态。[Docker 官方文档](https://docs.docker.com/desktop/features/wsl/) 对这些关系有清楚说明。

## 从较小的检查开始

我的诊断顺序通常从较小的检查开始：确认发行版名称和状态，尝试执行一个简单命令，再读取 Docker 的状态与相关日志。接着核对项目所在路径、当前分支和容器配置，确保自己观察的是同一份代码。每一步只回答一个问题，下一步由结果决定。

## 缩小修复范围

如果简单命令就失败，继续修改业务代码通常得不到有用证据；如果引擎可访问而只有某个容器失败，则应回到该容器的启动命令、依赖和日志。把范围缩小之后，修复动作才有明确目标，也能避免一次重启暂时掩盖了真正的问题。

## 保存工作，再操作环境

涉及终止或重启环境时，我会先保存工作。终止一个指定发行版、关闭全部 WSL 环境和注销发行版是不同操作，影响范围也不同。尤其是注销发行版会删除关联数据，不能当作普通重启使用。[Microsoft 官方文档](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) 列出了这些命令及其语义。

修复之后，我会重新执行最初失败的操作，并补做一项与目标相符的检查。恢复了一条简单命令，只能说明这一层恢复；业务容器是否正常，还需要它自己的证据。排障记录的价值，正是让这些结论保持清楚。
